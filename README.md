# Почему семь дней? Адаптивный выбор окна по Лепскому для признаков в рекомендательных системах

Это проект по заданию 1 «автоматизация построения признаков в рекомендательных системах».
Данные — Yambda-50M (Яндекс Музыка). Математическая часть с доказательствами вынесена в
`docs/lepski_window.pdf`, здесь — отчёт: откуда идея, что я сделал, что получилось и что нет.

## Откуда взялась идея

Я учусь на мехмате, на кафедре теории вероятностей, и последний год много занимался математической
статистикой — в первую очередь непараметрическим оцениванием. Если вкратце, там есть классический сюжет: когда оцениваешь
функцию по зашумлённым данным ядром с полосой пропускания *h*, маленькое *h* даёт большую дисперсию,
большое — смещение, и весь вопрос в том, как выбрать *h* по данным, не зная истинной гладкости.
Одно из любопытных решений — метод Лепского: берёшь сетку полос, расширяешь полосу, пока новая оценка
согласуется со всеми предыдущими в пределах их доверительных интервалов, и останавливаешься на первом
противоречии. Для этой процедуры есть так называемое оракульное неравенство: ты проигрываешь оракулу, знающему
оптимальную полосу, лишь логарифмический множитель.

Действительно не совсем очевидно, когда лучше смотреть на 7-дневное окно, а когда на 10-дневное.
Признак «сколько раз пользователь слушал артиста за последние *W* дней», делённый на *W*, — это же буквально
оценка текущей интенсивности событий прямоугольным ядром с полосой *W*. То есть инженерный вопрос
«какое окно брать» — это та самая задача выбора полосы пропускания, только для пуассоновского потока.
А для пуассоновских потоков адаптивный выбор окна тоже разобран — у Кутоянца и Спокойного (1999),
и в финансовой статистике его применяли для оценки интенсивности сделок. В рекомендательных системах
я такого не нашёл. Так что идея проекта: заменить ручную сетку окон адаптивным выбором по Лепскому и честно проверить, что из этого выйдет.

## Коротко о результате

Задача: предсказать, дослушает ли пользователь трек, который ему показала рекомендательная лента.
Тест — 348 903 строки, 3 059 пользователей, доверительные интервалы — парный бутстреп по пользователям.

| Модель | Счётчиков | AUC | LogLoss |
|---|---|---|---|
| M0 — ручные окна 1/7/30/∞ дней | 24 | 0.87156 | 0.40250 |
| M0_all — все 9 окон сетки 1…128/∞ дней | 54 | 0.87196 | 0.40193 |
| **M3+ — Лепский (r̂, log Ŵ, B)** | **18** | **0.87165** | **0.40235** |
| M3++ — Лепский + окно 1 день (добавлена post-hoc) | 24 | 0.87158 | 0.40248 |

- **H1 (адаптивное окно не хуже ручных, порог −0.002): подтверждена.** ΔAUC = +0.00010,
  95% ДИ [−0.00028, +0.00047].
- **H2 (адаптивное окно лучше ручных): не подтверждена.**
- Все четыре способа задать окно различаются на 0.0004 AUC. Адаптивное окно заменяет ручной выбор без
  потерь, с меньшим числом признаков и без человека, но не выигрывает: бустинг по нескольким фиксированным
  окнам выучивает адаптивность сам.
- Самое интересное оказалось не в метрике, а в том, какие окна выбирают данные: для лайков — почти всегда
  всю историю, для прослушиваний артиста — режимы длиной от недель до месяцев. Ручные семь дней не
  выбираются почти никогда.
- По дороге я нашёл утечку через семантику `timestamp`, из-за которой первый AUC был 0.98 (раздел 3).
  Это, пожалуй, самый полезный эпизод проекта.

## 1. Постановка

**Данные.** Yambda-50M: 10 000 пользователей за 10 месяцев, события `listen` (с долей прослушанного
`played_ratio_pct` и длиной трека), `like`, `dislike`, `unlike`, `undislike`, флаг `is_organic`
(органика или рекомендательная лента), маппинги трек → альбом и трек → артист. Я взял случайные
5 000 пользователей **со всей их историей** — 23.7 млн событий за 301 день. Повторное потребление здесь
сильное: среди прослушиваний из ленты 61% — повтор того же трека, 83% — того же артиста. Значит, и прямые,
и косвенные связи из условия задания есть что считать.

**Строка и метка.** Строка — прослушивание из рекомендательной ленты (`is_organic = 0`),
`y = 1[played_ratio_pct ≥ 50]` — это Listen+ по определению авторов датасета. Мне понравилась эта
постановка тем, что негативы в ней естественные: скип — это трек, который лента показала, а пользователь
не стал слушать. Не нужно генерировать кандидатов, и сравнение моделей не зависит от того, как именно
я их сгенерировал. 68% положительных, 11.0 млн строк.

**Разбиение.** Глобальное по времени с зазорами в день: train — дни 0–277, val — 279–292 (718 тыс.),
test — 294–300 (349 тыс. строк, 3 059 пользователей). Для обучения я взял случайные 20% train-строк
(2 млн) — больше не нужно, а памяти жалко; val и test — целиком. Гиперпараметры подбирал только
early stopping на val, test трогал один раз.

**Метрики.** ROC-AUC и LogLoss. Интервалы для разностей — парный кластерный бутстреп по пользователям
(500 повторов): строки одного пользователя зависимы, и бутстреп по строкам дал бы слишком узкие интервалы.

## 2. Признаки и «только прошлое»

Каждый признак строки с моментом предсказания *t\** зависит только от событий с `ts < t*` (строго)
и от статистик по train-периоду. Реализовать это оказалось проще, чем я думал: один примитив
`PITCounter.count_before(key, s)` — число событий ключа с `ts < s` — на отсортированном логе через
два `searchsorted`. Любой оконный счётчик — разность двух таких значений.

**Общий блок Φ0 (12 признаков, один для всех моделей):** число прослушиваний и лайков пользователя, число
рекомендательных прослушиваний и сглаженная доля дослушиваний среди них, дней с первого события, часов с
последнего прослушивания; популярность трека и артиста по всем пользователям до *t\**, сглаженная доля
дослушиваний трека; длина трека; час; день недели.

**Счётчики пар** — для уровней связи {трек, альбом, артист} × типов событий {прослушивание, лайк}.
Уровни я не выбирал руками, а перечислил из схемы данных: это все отображения «трек → атрибут», которые
там есть.

| Блок | На (уровень, тип) | Всего |
|---|---|---|
| ручные окна 1/7/30/∞ дней, log(1+N) | 4 | 24 |
| сетка окон 1, 2, 4, …, 128, ∞ дней | 9 | 54 |
| Лепский: r̂ (интенсивность в выбранном окне), log Ŵ, B (сила перелома) | 3 | 18 |

**Проверки.** Два теста, оба в `src/leakage_phase1.py`: 24 оконных счётчика совпадают с грубой силой
(фильтр pandas по строке) на случайных строках; после удаления из лога всех событий с `ts ≥ t*` ни один
признак не меняется. Плюс `src/synthetic_check.py` для самого критерия: на однородных пуассоновских потоках
при теоретическом пороге окно не обрезается ни разу (граница ≤ δ выполнена с запасом), при пороге вчетверо
меньше — около 5% обрезаний; на потоках со скачком интенсивности мода выбранного окна совпадает
с оракульным.

## 3. Утечка, которую я чуть не пропустил

Первый прогон дал AUC 0.98. Я обрадовался секунд на десять, потом понял, что для задачи «дослушает ли
человек трек» это невозможно. Тест «удалить будущее» проходил — значит, утечка была не через события из
будущего, а через что-то в определении момента предсказания.

Я написал диагностику (`src/diag_timestamp.py`): для тестовых строк посчитал разрыв между `timestamp`
строки и предыдущим событием пользователя. У дослушанных треков этот разрыв оказался равен ровно длине
трека — медиана `gap_prev / track_len` = 1.00; у скипнутых — 6% длины. То есть `timestamp` в Yambda —
момент **окончания** прослушивания, а следующий трек начинается ровно там, где закончился предыдущий.
Считая признаки «на момент *t*», я давал модели длительность текущего прослушивания, то есть метку:
один признак «часов с последнего прослушивания» даёт AUC 0.87, а вместе с длиной трека бустинг добирает
до 0.98.

Исправление концептуальное, а не косметическое: момент предсказания — **начало** прослушивания,
`t* = timestamp предыдущего прослушивания пользователя` (если его нет — `t − track_len`). Медианный сдвиг
получился 175 секунд. Заодно это исключает лайки, поставленные во время текущего трека (у 20% строк есть
события пользователя в ту же секунду). Вывод, который я для себя сделал: стандартный тест на утечки
проверяет, что ты не смотришь в будущее, но не проверяет, что ты правильно понимаешь, где у данных
настоящее.

## 4. Метод

Полностью, с доказательствами, в `docs/lepski_window.pdf`. Идея в нескольких строках.

Оконный счётчик `N_W / W` оценивает текущую интенсивность μ₀ событий пары с риском (смещение)² + μ/W.
Для сетки окон W₁ < … < W_J и k < j я проверяю однородность двух отрезков — старого [t−W_j, t−W_k)
и свежего [t−W_k, t) — критерием отношения правдоподобия для двух пуассоновских частот:

`T_jk = W_k · KL(r̂_k ‖ r̂_j) + (W_j − W_k) · KL(r̂_old ‖ r̂_j)`, где `KL(a‖b) = a·log(a/b) − a + b`.

Это замкнутая формула, и она правильно ведёт себя на пустых коротких окнах (наивная «разность средних»
там ломается — об этом есть замечание в PDF). Правило Лепского: `ĵ = max{ j : T_jk ≤ z для всех k < j }` —
самое широкое окно, которое не противоречит ни одному более узкому. Признаки: интенсивность `r̂ = N_ĵ / W_ĵ`,
`log W_ĵ` — сколько времени пара «в текущем состоянии», и `B` — статистика теста, остановившего
расширение, то есть сила перелома.

Что я доказал (теоремы 6 и 8 в PDF, через неравенство Чернова для пуассоновских счётчиков и оценку KL
снизу квадратом разности): при `z = 2·log(4J/δ)` однородная пара не обрезается с вероятностью ≥ 1−δ,
а на этом событии адаптивная оценка отклоняется от μ₀ не более чем на величину порядка `(1+√(2z))·√(μ₀/W*)`,
где W* — оракульное окно. Это и есть классическая цена адаптации ~ √log J.

Единственный параметр — порог z. Теоретический z_th = 13.2 (J = 9, δ = 0.05) консервативен, поэтому
я перебрал z_th, z_th/2, z_th/4, z_th/8 по LogLoss на валидации.

Для контекста — чем это отличается от других способов задать окно: ручная сетка (ноль параметров,
окно не зависит от истории пары); подбор по валидации (десятки переобучений); экспоненциальное затухание
и процессы Хоукса (один параметр, но окно «слепо» к рисунку истории — зависит только от того, когда были
события); BOCPD (три параметра, мягкое байесовское усреднение по началу режима). Лепский — один параметр,
жёсткий выбор, оракульная гарантия, ноль переобучений.

## 5. Эксперимент

Все модели — один и тот же LightGBM (num_leaves 63, lr 0.05, min_data_in_leaf 200, L2 = 5,
feature/bagging fraction 0.8, early stopping 100 на val) с общим блоком Φ0; различаются только счётчиками.

Про M0_all. Я хотел снять возражение «может, ты просто плохо выбрал ручные окна». Вместо дорогого жадного
отбора я отдал бустингу все девять окон сетки: любой ручной набор — подмножество этих признаков, так что
M0_all — верхняя граница любого ручного выбора ценой одного обучения.

Модель M3++ я добавил после первого прогона, чтобы проверить гипотезу из таблицы важностей (раздел 6.3).
Честно помечаю её как post-hoc.

## 6. Что я из этого понял

### 6.1 Сравнение

Четыре способа задать окно различаются на 0.0004 AUC и 0.0006 LogLoss. H1 выполнена с запасом:
18 адаптивных счётчиков без выбора окна человеком эквивалентны 24 ручным. H2 отвергнута. Единственная
значимая разность — M0_all над M0: девять окон чуть лучше четырёх. В PDF я заранее описал три возможных
исхода; это второй: адаптивность экономит признаки и решения, но информации не добавляет.

### 6.2 Какие окна выбирают данные

Распределение Ŵ по тестовым строкам при z = 1.64:

| уровень, событие | 1d | 2d | 4d | 8d | 16d | 32d | 64d | 128d | ∞ |
|---|---|---|---|---|---|---|---|---|---|
| трек, прослушивание | .005 | .008 | .025 | .013 | .035 | .072 | .108 | .116 | .618 |
| альбом, прослушивание | .010 | .018 | .043 | .030 | .056 | .088 | .115 | .116 | .523 |
| артист, прослушивание | .042 | .053 | .082 | .069 | .094 | .115 | .115 | .099 | .330 |
| трек / альбом / артист, лайк | ≈0 | ≈0 | ≤.01 | ≤.005 | ≤.01 | ≤.014 | ≤.018 | ≤.031 | .99 / .98 / .91 |

Три вещи, которые мне кажутся содержательными. Во-первых, для лайков окно почти всегда — вся история:
лайки редки, короткие окна пусты, критерий не находит противоречий. Это ровно то поведение на разреженных
парах, ради которого я выбирал форму критерия. Во-вторых, чем выше уровень связи, тем «режимнее»
поведение: для артиста только треть строк в полной истории, остальное размазано по 4–128 дням — интерес
к артисту действительно живёт режимами длиной в недели и месяцы. В-третьих, окна в 1–2 дня выбираются
в 1–10% случаев, а ручные семь дней (между точками 4 и 8) почти не востребованы. Если бы меня спросили
«какое окно брать для этой задачи», честный ответ по данным: всю историю, а там, где короче, — недели.

### 6.3 Почему адаптивное окно не выиграло

Таблица важностей в M0_all двугорбая: для прослушиваний трека важны окна 64/128/∞ дней и окно 1 день,
для артиста — 1 день и 32/∞. Я предположил, что сигнал живёт на двух масштабах — «слушал сегодня» и
«слушал вообще», — а одно адаптивное окно, которое в 60% случаев равно полной истории, информацию
«сегодня» теряет. Проверка — модель M3++ (Лепский плюс окно в 1 день, 24 счётчика как у M0).
Гипотеза не подтвердилась: M3++ не отличается от M0 и статистически уступает M0_all.

Значит, дело не в двух масштабах. Преимущество полной сетки в том, что бустинг из девяти вложенных окон
строит собственные отношения и разности — 16 дней против 64, 2 против 32 — то есть свою, более тонкую
адаптивность, чем жёсткий выбор одного окна. Один адаптивно выбранный счётчик, даже с возрастом состояния
и статистикой перелома, эту структуру не передаёт. Это ограничение парадигмы «одно окно на пару»,
и оно относится к ручному выбору одного окна так же, как к адаптивному.

### 6.4 Порог z

Качество монотонно улучшается при уменьшении z от 13.2 до 1.64, но между 3.29 и 1.64 разница 4·10⁻⁵ —
плато. Теоретический порог консервативен (объединение по тестам плюс Чернов), что видно и на синтетике:
при z_th ноль обрезаний вместо допустимых пяти процентов.

### 6.5 Ограничения

- Одно разбиение по времени и одна подвыборка пользователей: бутстреп учитывает дисперсию по пользователям,
  но не по периодам.
- Рекомендательные прослушивания порождены политикой рекомендателя, а счётчики я строил по всем событиям.
- Окно берётся из дискретной сетки и жёстко; взвешенное усреднение по принятым окнам я не проверял.
- Недельная периодичность внутри окон ≥ 1 дня не моделируется.
- Экспоненциальное затухание и BOCPD не сравнивались — они описаны в PDF как альтернативные принципы
  и остаются продолжением.

## 7. Ближайшие работы

Метод Лепского и его пуассоновские версии (Лепский 1990; Спокойный 1998; Кутоянц–Спокойный 1999;
Рейно-Буре 2003) — не моё; оракульные неравенства — тоже. Адаптивное окно для пуассоновской интенсивности
применялось в финансовой статистике (Khowaja, Saef, Sizov, Härdle 2020). В рекомендациях ближайшее, что
я нашёл: патент Yahoo на «адаптивное окно обратной связи», где окно подстраивается под объём данных
эвристикой без критерия; свежая эмпирика по дизайну окон для бустинга (Pinchuk 2025), где «окно по числу
событий» — грубая форма адаптивности; и CUSUM-подходы, отбрасывающие историю до смены предпочтений
(Hariri и др. 2015). Что я считаю своим: переформулировка выбора окна как выбора полосы с явным оракулом,
адаптивное окно по Лепскому для каждой пары как замена сетки в ранжирующей модели, выбранное окно
и сила перелома как признаки, гарантия в терминах оконной сетки и контролируемое сравнение на Yambda.

## 8. Выводы

1. Построение оконных признаков можно полностью снять с человека: уровни связи перечисляются из схемы,
   окно выбирается статистическим критерием с одним параметром, качество не теряется.
2. Для этой задачи выбор окна почти не важен. «Почему семь дней?» — потому что при наличии окна
   «вся история» и хотя бы одного короткого это не имеет значения.
3. Информативнее самого признака оказалось распределение выбранных окон: оно показывает, на каких
   масштабах живёт интерес к треку, альбому и артисту, и даёт эмпирическое обоснование любому ручному
   окну — или показывает его отсутствие.
4. Больше всего в честность результата вложил не метод, а проверка семантики времени. Без неё я бы
   сравнивал способы угадать метку.

## 9. Воспроизведение

```bash
python3.11 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt          # macOS: сначала brew install libomp

# фаза 0: данные (скачивание ~450 МБ), EDA, разбиение, строки, тест на утечки
python -m src.data && python -m src.eda && python -m src.rows && python -m src.leakage
# диагностика семантики timestamp (раздел 3)
python -m src.diag_timestamp
# фаза 1: проверки без данных, признаки, тест на утечки, обучение и оценка
python -m src.synthetic_check
python -m src.leakage_phase1 --synthetic
python -m src.features.build
python -m src.leakage_phase1
python -m src.train_eval                 # -> results/summary.md, metrics.json, w_hist.csv, importance_windows.csv
```

Все параметры — в `configs/base.toml`. Прогон на синтетике без скачивания:
`python -m src.fake_data && python -m src.data --local …`.
